# 架构与功能说明

这份文档回答两个问题：**它到底有哪些功能**，以及**这些功能是怎么拼起来的**。
README 讲"为什么这么设计"，这里讲"实际怎么运转"——包括触发条件、落盘位置、返回值和失败行为。

对应版本：`0.1.0`（与 `package.json` 一致）。

---

## 1. 定位

一个**无界面**的陪伴式对话引擎。输入一句话，输出 1~3 条短消息；平时自己判断要不要先开口。

```
宿主（UI / IM / 终端）
   │  say(text) / tick() / forceSpeak()
   ▼
bigfish-chat  ← 人设、记忆、检索、主动开口、记账
   │  HTTPS
   ▼
OpenAI 兼容接口（默认 DeepSeek /chat/completions）
```

它不渲染、不联网监听、不管理会话路由。**谁调用它，谁负责显示和收发。**

## 2. 功能清单

### 2.1 对话

| 功能 | 行为 | 代码 |
|---|---|---|
| 单轮对话 | `say(text)` → `{ ok, segments, reply, usage }` | `index.js` |
| 多段回复 | 按换行拆成 1~3 条，超过 3 条时把剩下的并进最后一条 | `splitSegments()` |
| 说话带动作 | 偶尔在句子里带一句括号旁白（`（尾巴动了一下）`），原样进回复；`action:false` 全关 | `prompt.js` `ACT_GUIDE` |
| 旧标签清理 | 模型偶尔还写 `#动作:类别`，抠掉；括号旁白保留 | `stripActionTags()` |
| 时间感知 | 每轮读本机时间，给到 `10月25日周日 19:06`，只对当轮有效 | `initiative.js` `timeLine()` |
| 历史窗口 | 默认只带最近 2 轮原文；被挤掉的压成一行话题提要（最多 4 句） | `index.js` |
| 输入清洗 | 去首尾空白、截断到 500 字 | `index.js` |
| 超时 | 默认 30 秒，超时返回 `ok:false`，不抛异常 | `llm.js` |
| 思考档位 | `off` / `low`（默认）/ `on`；`low` 额外在提示词里限定"一句话想完" | `config.js` `llm.js` |
| 兼容性兜底 | 接口不认 `thinking` 字段（400/422）时，去掉它重发一次 | `llm.js` |
| 失败不崩 | 网络错误、超时、空回复都返回 `{ ok:false, message }` | `llm.js` |

### 2.2 记忆

| 功能 | 行为 | 代码 |
|---|---|---|
| 原始留档 | 每轮一行 JSON，落 `raw/YYYY-MM-DD.jsonl`，不花 token | `memory.js` |
| 待整理队列 | `record()` 同时写 `.pending.json`，进程崩了下次启动能补 | `memory.js` |
| 自动整理 | 最后一次说话后静默 10 分钟触发；`close()` 也会触发 | `memory.js` |
| 分批整理 | 一次整理的对话超过 3800 字符就按轮切批、逐批调用；每批各自 2~6 条 | `memory.js` |
| 三档日记 | `[重点/标签]` / `[日常]` / `[简记]`，2~6 条、每条 ≤30 字 | `memory.js` |
| 永久层 | 只有 `[重点/约定]` 进 `pinned.md`，永不衰减 | `memory.js` |
| 长期叫法 | 14 天内、至少 3 个不同日期都出现过的外号，单独提 60 字 | `memory.js` |
| 周摘要 | 4 天以前的日记按 ISO 周压成 2~5 行，存 `diary/weekly/` | `memory.js` |
| 月摘要 | 已过完的自然月压成 2~3 行，存 `diary/monthly/`，默认留 12 份 | `memory.js` |
| 三日复核 | 满 3 天（30 天内）的日记只调级别/标签，不删不改正文 | `memory.js` |
| 注入预算 | 总 1400 字，pinned → 称呼 → 近三天（留 25% 保底给更早）→ 周 → 月 → 相关旧事 | `memory.js` |
| 相关旧事检索 | 默认 365 天内字面匹配（2~4 字滑窗 + 标签词 + 别名），最多 3 条 | `memory.js` `recall.js` |
| 二次展开 | 命中后追问才去那天 `raw/` 捞原话，带遗忘概率与字数衰减 | `memory.js` `recall.js` |
| 失败重试 | 整理失败写 `errors/errors.log`，5 分钟后重试；连续 4 次停手 | `memory.js` |

### 2.3 主动开口

| 功能 | 行为 | 代码 |
|---|---|---|
| 定时询问 | 宿主定时调 `tick()`，它只回答"这次说不说" | `initiative.js` |
| 在场判定 | 由宿主注入 `isHere()`；不注入 = 一直在 | `initiative.js` |
| 频率 | 每天 6 次，间隔 90~180 分钟随机 | `initiative.js` |
| 静默时段 | 0:00~6:00 不主动，可配，支持跨零点 | `initiative.js` |
| 刚聊过不插嘴 | 用户 10 分钟内说过话，这次跳过 | `initiative.js` |
| 手动开口 | `forceSpeak()` 不占额度、不算"被晾着"，但会推迟 20 分钟 | `initiative.js` |
| 接话判定 | 三条判据（明着指回 / 短接话 / 共同实词），按内容不按时间 | `initiative.js` |
| 被晾计数 | 连续几次没被接住就累积，最多 5 | `initiative.js` |
| 情绪注入 | 只给事实（几次、原话），方向交给模型；接住后留 2 小时余味 | `initiative.js` |
| 自述留档 | `said/*.md`（给人看）+ `self/*.jsonl`（给它自己接话头） | `index.js` `said-store.js` |

### 2.4 工程件

| 功能 | 行为 | 代码 |
|---|---|---|
| 配置 | JSONC（允许注释）、默认值合并、坏值归一化 | `config.js` |
| 记账 | 四类调用（对话/整理/主动/预热）逐笔落 `usage/usage-YYYY-MM-DD.jsonl`，90 天清理 | `usage.js` |
| 计时 | 只有两个内部定时器：整理空闲计时、失败重试计时 | `memory.js` |
| 无轮询 | 主动开口**不自己起定时器**，必须宿主调 `tick()` | — |
| 零依赖 | 只用 Node 内置 `fs` / `path` / `fetch` | — |

### 2.5 它不提供

- 流式输出（一次返回完整回复再拆条）
- 工具调用 / 函数调用 / 联网搜索
- 多用户会话（一个实例 = 一个 `dataDir` = 一个人）
- IM 适配（QQ / 微信 / Telegram 都要自己写收发层）
- 内容审核、指令系统、权限控制
- 数据库（全部是本地文件）

## 3. 模块与依赖

```
index.js                 对外门面：say / tick / forceSpeak / warmup / close
├── config.js            默认值、JSONC 解析、坏值归一化
├── llm.js  ────────────► config.js（取值范围）
├── persona.js           内置人设（鲸鱼娘，可整段替换）
├── prompt.js            系统提示拼装：固定前缀在前，动态内容在后
├── memory.js ───────────► recall.js（遗忘曲线、追问判定、原话截取）
├── initiative.js        主动开口：在场、频率、静默、被晾、情绪
├── usage.js             token 账本
└── said-store.js        自述话语目录 + 旧版迁移
```

`presence.js` 是**可选**的：它只提供"光标多久没动"的采样工具，宿主可以直接用自己的实现，不注入也能跑（默认永远算"在"）。

依赖方向是单向的：`index` 认识所有模块，模块之间只有 `memory → recall`、`llm → config` 两条边。所以每个模块都能单独 `require` 出来用：

```js
const { modules } = require('bigfish-chat');
const mem = modules.memory.createMemory({ dir: './memory', complete });
```

## 4. 一次对话的完整链路

```
say(text)
  │
  ├─1 空文本 / 没 key → 直接返回 ok:false（不花钱）
  │
  ├─2 initiative.onUserChat(text)
  │     判断这句是不是在接它刚才那句
  │     ├ 接住 → ignored 清零、标记 self 里那条 heard、留 2 小时余味
  │     └ 没接 → 如果本来就在堵着，续 2 小时
  │     无论接没接：lastUserChatAt = now
  │
  ├─3 history 裁剪（超过 historyTurns 的压成 digest）
  │
  ├─4 拼 system prompt（见 4.1）
  │
  ├─5 POST /chat/completions  ← 唯一花钱的地方
  │     失败 → 返回 ok:false，不写记忆、不进历史
  │
  ├─6 成功：push user + assistant 到 history，再裁一次
  │
  ├─7 splitSegments(reply) → 1~3 条
  │
  └─8 memory.record(user, 拼接后的回复)
        ├ raw/今天.jsonl 追加一行
        ├ .pending.json 更新
        └ 重置 10 分钟空闲计时器
```

### 4.1 系统提示的顺序（缓存纪律）

```
1. 人设                    固定（启动时抽一次样例，之后不再变）
2. 思考要求（thinking=low） 固定
3. 动作说明（action）        固定；action:false 就不加
4. 记忆块                  每句都变 ← 缓存从这里断开
5. 更早话题提要（digest）    每句都变
6. 它自己刚说的话（self）    每句都变
7. 情绪（moodLine）         每句都变
8. 现在几点（timeLine）      每句都变，但只在最末尾
```

缓存按 token 前缀命中，**前缀一变后面全按未命中价算**。所以固定的第 1~3 段必须在最前面，且不能在运行中重抽——`persona` 只在 `createChat()` 时生成一次。

时间放最末尾是有意的：每轮分钟都在变，但只影响最后十几个 token，前缀照样命中（实测命中率 ~75%）。要是放在人设旁边，等于每句都按未命中价算。

### 4.2 系统提示里各块的作用

| 块 | 内容 | 上限 |
|---|---|---|
| 动作 | 括号旁白的写法约定 + 示例 + 频率（四五句一次） | ~120 字 |
| 记忆 | 见 5.3 的注入顺序 | 1400 字 |
| digest | 被挤出历史的话题，只留用户问的 | 4 句 |
| self | 它自己 12 小时内说过的话，能接才给 | 90 字 |
| mood | 被晾着这件事，只给事实（哪句没接） | 几十字 |
| time | `现在是10月25日周日 19:06。` | 20 字 |

## 5. 记忆子系统

### 5.1 数据流

```
对话 ──record()──► raw/YYYY-MM-DD.jsonl       （原话，永久保留，不注入）
     └──────────► .pending.json               （待整理队列）
                        │
             静默 10 分钟 / close()
                        ▼
                 整理（温度 0.3，关思考）
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
  diary/日期.md    pinned.md        self 里的 d=1
  （三档日记）     （重点/约定）      （标记已消化）
        │
        ├─ 4 天以后、没消化 ──► diary/weekly/2026-W42.md
        ├─ 月末过完 31 天 ────► diary/monthly/2026-08.md
        └─ 3 天后、30 天内 ──► 复核（只调级别/标签）
```

### 5.2 整理与复核的触发条件

| 动作 | 触发 | 频率限制 | 失败处理 |
|---|---|---|---|
| 整理 | 最后一条记录后静默 `memoryIdleMinutes`（默认 10） | 一次只跑一轮，新记录等下一轮；单轮内部按 3800 字符切多批 | 写 `errors/errors.log`，5 分钟后重试，连续 4 次停 |
| 复核 | 整理完成后顺带跑 | 每次只处理 1 天；3~30 天窗口；`.reviewed.json` 去重 | 标记 `failed`，6 小时后重试 |
| 周摘要 | 整理完成后顺带跑 | 只处理 4 天以前且未消化的日期 | 失败下次再来（不标记） |
| 月摘要 | 周摘要之后顺带跑 | 只处理已过完 31 天的自然月，一次最多补 3 个月 | 失败不标记，下次再来 |

复核的日期窗口是 `(今天-30, 今天-3]`。**它只改方括号里的级别和标签**：正文、时间、别名、`（心里：…）` 全部原样保留。降下来的条目仍留在文件里，检索照样能翻到。

### 5.3 注入顺序与预算

`memory.context(userText)` 按顺序拼，总上限 `memoryMaxChars`（默认 **1400**）：

| 顺序 | 内容 | 预算 | 条数 |
|---|---|---|---|
| 1 | `pinned.md` | 220 字（从最新往回取） | 不限 |
| 2 | 长期叫法 | 60 字 | 最多 2 条（不同叫法，最近用过的跳过） |
| 3 | 今天 | 400 字 | 8 条（重点 ≤6、简记 ≤2） |
| 4 | 昨天 / 前天 | 每天 260 字 | 5 / 4 条，只含重点+日常 |
| 5 | 周摘要 | 220 字 | 最近 `memoryWeeklyKeep` 份（默认 **26** ≈ 一年） |
| 6 | 月摘要 | 200 字 | 最近 `memoryMonthlyKeep` 份（默认 12 ≈ 一年） |
| 7 | 相关旧事 | 3 条 | 见 5.4 |
| 8 | 二次展开片段 | **绕过总预算**（约 150 字） | 每次最多 1 段 |

排序权重是 `KIND_BASE(kind) + TAG_WEIGHT(标签)`：重点 30 / 日常 20 / 简记 10，标签只在重点内部比高低。这样 `[日常/用户]` 不会压过 `[重点/其它]`。

名额不纯按分数抢：重点最多占 `dayLimit-2` 个（今天 6、昨天 3、前天 2），剩下的位置必须给日常和简记。纯按重要度排会让"约定"吃满全部名额，记忆里长期只剩那几条，说话也就只剩那几句可念。

**近期日记花不完整份预算 —— 这是这一版最重要的改动。** 以前所有段落共用一个上限、先到先得，而周摘要排在今天/昨天/前天后面；光前几段的上限加起来就超过总上限，于是只要这几天写得满，周/月摘要永远抢不到，看起来就像它彻底忘了三个月前的事。现在预留 `oldReserve = max(360, 25% × 上限)`：近期日记只能在 `cap - oldReserve` 以内花，剩下的必定留给"更早"。周/月两段再分这笔保底 —— 预算上先给月留 55%（它管最长跨度），注入时仍按周→月由近到远排。

`context()` 结果按「日期 + 这句原文」缓存；跨过午夜会自动失效（否则"今天"会指到昨天）。

### 5.4 检索与二次展开

**第一步：字面检索**（纯本地，零成本）

- 输入短于 3 字直接返回空
- 分词：2~4 字滑窗，含虚词字整条丢弃，再滤掉"自己/今天/事情"这类到处都是的词
- 同时匹配：标签词表（吃/累/困/喜欢/答应…）、正文 `includes`、整理时写的 `#别名`
- 范围：最近 `memoryRetentionDays` 个日记文件（默认 60），跳过最近 3 天（那几天本来就全量注入）
- 计分：标签 +2、正文命中 +词长、别名命中 +3、重点 +2、日常 +1
- 去重：同一 `(日期, 标签)` 只留最高分 1 条（同一天同一类事常有七八条，不去重名额会被占满）
- 分桶：按"多久以前"分三桶（0~30 / 30~180 / 180+ 天），每桶各出 1 条，空桶再由剩余高分补满。
  只按分数排的话同分日期新的永远赢 —— 实测 3 年 1 万条里问「加班」捞回的全是最近两三天的
- 取 3 条

**第二步：二次展开**（命中后，且宿主/用户追问）

三道闸必须同时满足：

1. **追问触发**：句子 ≤18 字，且含"后来 / 然后呢 / 那后来 / 继续 / 接着 / 讲完 / 说完 / 结果呢 / 下文 / 再然后"之一。长句里的"后来"不算
2. **概率衰减**：`forgetProb(天数, 档位)`，重点 ×1.25 / 日常 ×1.0 / 简记 ×0.85
3. **字数衰减**：1~3 天 150 字、14 天内 90、30 天内 50、更久 24

再加两道限流：**10 分钟冷却**、**只展开第一条命中的那天**。展开内容单独成块，不占 1400 字预算。

| 距离 | 概率 | 字数 |
|---|---|---|
| 1 天 | 0.98 | 150 |
| 3 天 | 0.90 | 150 |
| 7 天 | 0.78 | 90 |
| 14 天 | 0.62 | 90 |
| 30 天 | 0.42 | 50 |
| 60 天 | 0.28 | 24 |
| 更久 | 0.15 | 24 |

零命中就返回空 —— 宁可它真的忘了，也不硬编一个印象。

### 5.5 它自己的话怎么进提示

`memory.selfBlock(userText)`：

- 用户这句话 ≥12 字（像在问正经事）→ 整块跳过
- 12 小时内：被接住的 1 条原话 + 没被接的 2 条原话（每条截 16 字）
- 12~48 小时：只在没有原话时，给一句统计（"主动开口 4 次，3 次没接"）
- 48 小时以上：不注入
- 总预算 90 字

`kind: 'gift'` 的记录如果有 `text`，注入时写成「你留了个小东西「会冒泡的深海灯」」；
没有 `text` 才退回文件名。**别把文件名当描述** —— 文件名只有日期，等于什么都没记住。

### 5.6 这份实现与桌宠版的差别

同一个作者、同一套思路的两个落点：这份是**无界面框架**，桌宠版把同一套记忆接在 Electron 上。
记忆的骨架（三档、遗忘曲线、追问才展开、周/月摘要、预算与保底）两边一致，下面这些是**只有桌宠版有**的：

| 机制 | 桌宠版 | 这里 |
|---|---|---|
| 日记压缩（一天 >12 条合并到 ≤8 条） | 有 | 没有：宁可多几条，也不冒着压掉手写行的风险 |
| `pinned.md` 时间戳账本 / 同行替换 / 超期归档 | 有 | 没有：仍是纯追加 + 从末尾往回取 |
| 跨天去重（同一件事只注入一次） | 有 | 没有 |
| 它自己的动作不回流成记忆（`isSelfAction`） | 有 | 没有 |
| 生成礼物 / 心事文件 | 有 | 没有：宿主自己写 `kind:'gift'` / `'thought'` 记录即可，注入与素材都认得 |
| 只读看一眼本地文件（白名单 + mtime 去重） | 有（`peek.js`） | 没有：框架不碰宿主的文件系统 |

**没有不等于欠账**：压缩和去重都是"用代码替模型判断"，桌宠版需要是因为它一天能聊几十轮；
框架默认一天 2~6 条日记，压不压差不多。要接一个高频宿主，先看 §5.3 的保底预算够不够，再考虑搬那几层。

## 6. 主动开口子系统

### 6.1 `tick()` 的判定顺序

顺序不能调换 —— 前面的闸更便宜（纯本地），也更能避免"白花一次钱"。

```
1. enabled?        否 → { skipped: 'disabled' }
2. 正在生成?        是 → { skipped: 'busy' }
3. 跨日重置额度
4. 静默时段?        是 → { skipped: 'quiet' }
5. 人在不在?        不在 → { skipped: 'away' }
6. 今天额度用完?    是 → { skipped: 'speak-limit' }
7. 还没到间隔?      是 → { skipped: 'speak-gap' }
8. 10 分钟内刚聊过? 是 → { skipped: 'just-chatted' }
9. 生成 → { ok: true, kind: 'speak', text }
```

`skipped` 的完整枚举就是上面这 7 种，宿主可以直接拿去打日志或做状态显示。

### 6.2 状态机

```
                 ┌──────────── 额度/间隔/静默/不在 ────────────┐
                 ▼                                            │
 idle ──tick 通过──► 生成中 ──成功──► 说完（设置下次间隔） ─────┘
   ▲                    │
   │                    └─失败──► 不计数，等下一次
   │
   └── 用户说话（onUserChat）：接住了 → ignored=0；没接 → 保持
```

- **被晾计数**：每次自动开口前，如果上次说完之后用户一直没说话，`ignored += 1`（最多 5）。手动触发不计数
- **提这件事**：`ignored >= 2` 时，接下来两小时里系统提示会带一句"你说的哪句他没接"（`sulkUntil` 每次续 2 小时）
- **不再提**：被接住了（`sulkHeardAt`）就不提；或者你连着聊 3 句（`chatStreak >= 3`），也算真在陪它，只留 30 分钟
- **注意**：上面三条都只决定"还提不提这个事实"，不决定语气软硬。程序不管它这会儿是冷淡还是照常

### 6.3 接话判定的三条判据

```
1. 明着指回：你刚才 / 你说的 / 你说啥 / 听见没 / 那张纸 / 字条 …
2. 短接话：嗯 / 哦 / 对 / 真的吗 / 然后呢，且距它说完 ≤5 分钟
3. 共同实词：两边都有 2 字以上的实词（滤掉"现在/就是/什么"）
```

三条都不中 = 没接。宁可漏判一次"他其实在理我"，也不能把"他在聊别的"算成"他在回应我"。

### 6.4 "被晾"这件事怎么注入

`moodLine()` 只给一条事实，一个字都不提"你该怎么样"：

> （你主动说的「喂，在不在」，他没接。）

2026-10-24 之前的版本写的是"别装作什么都没发生，也别一下又贴上去。是有点气、还是有点难受，你自己定"——
名义上把方向交给模型，实际已经替它排好了一场必须演的反应：不生气就等于"装没事"。
按用户要求删掉了。理不理这句、下句冷不热，它自己决定。

`unheardHint()`（主动开口那条线）同理，只陈述"你说过几次、他都没回"。

不注入的情况：超过 3 小时没来（提也无意）、已经被接住（历史里就有它那句和对方回应）、
或者这段里它自己的话已经翻不到了（`recentSaid` 空）。

**`sulkUntil` 管的是"还提不提这件事"，不是情绪强度。** 程序不量化"有多生气" ——
一旦成了数值，它就得按数值表演，反而更假。

### 7.1 文件格式

`raw/*.jsonl`（一行一轮，`anim` 只有宿主传了才有）：

```json

```

`diary/*.md`：

```
- 09:20 [重点/喜好] 用户不吃香菜，从小就不吃 #香菜
```

## 9. 返回结构与错误处理

### 9.1 返回值

| 调用 | 成功 | 失败 |
|---|---|---|
| `say()` | `{ ok:true, reply, segments, usage, reasoningTokens }` | `{ ok:false, message }` |
| `tick()` | `{ ok:true, kind:'speak', text }` | `{ skipped:'<原因>' }` |
| `forceSpeak()` | 同上 | `{ ok:false, reason }` / `{ skipped }` |
| `warmup()` | `{ ok:true, ... }` | `{ ok:false, message }` |
| `close()` | `{ ok:true }` | `{ ok:true, skipped:true }`（没东西可整理） |
| `systemPrompt(text)` | 直接返回拼好的 system 字符串（调试用） | — |
| `state()` | 见下 | — |

`state()`：

```js
{
  dataDir,
  historyTurns,        // 当前带了几轮
  digest,              // 被挤掉的话题提要
  pendingMemory,       // 还没整理的段数
  initiative: {        // 主动模块
    quiet, quietStart, quietEnd, peak,
    speakToday, speakPerDay, nextSpeakInMin,
    ignored, sulk, lastSpeakAt, lastUserChatAt
  },
  usageToday: { total, prompt, cached, completion, calls, day, byKind }
}
```

`byKind` 的每一项是 `{ calls, total }`，例如 `{ 对话: {calls:12,total:5400}, 整理: {...} }`。

### 9.2 失败策略

| 情况 | 行为 |
|---|---|
| 没有 key / 空输入 | 立即返回，不发请求 |
| API 超时 | 30 秒中断，返回 `请求超时` |
| API 4xx/5xx | 返回 `API <状态码>：<前 160 字>` |
| 返回空内容 | 返回 `模型没有返回内容` |
| `thinking` 字段不被识别 | 去掉该字段重发一次（只重发一次） |
| 记忆写盘失败 | 记日志，功能降级，不影响对话 |
| 整理失败 | `errors/errors.log` + 5 分钟后重试（最多 4 次） |
| 复核失败 | `.reviewed.json` 标 `failed`，6 小时后重试 |

**所有对外方法都不抛异常。** 宿主拿 `ok` 判断即可。

## 10. 并发、定时器与生命周期

### 10.1 并发

| 场景 | 现状 |
|---|---|
| 同一实例并发 `say()` | **没有队列**。两次调用会各自拼历史、各自发请求，返回顺序可能错乱 |
| `tick()` 并发 | `busy` 标志挡住，第二次返回 `skipped:'busy'` |
| 并发 `flush()` | 后一次等前一次结束，再检查有没有新记录 |
| 并发复核 | `reviewing` 锁，撞上就跳过（那天下次还会轮到） |
| 并发周摘要 | `weeklyBusy` 锁 |

**给宿主的建议**：同一个用户的消息按顺序 `await`（一条 Promise 链），不要并发调 `say()`。

### 10.2 定时器

内部只有两个 `setTimeout`：

1. **整理空闲计时**：每次 `record()` 重置，到点触发 `flush()`
2. **失败重试计时**：整理失败后 5 分钟

**没有轮询。** 主动开口完全靠宿主调 `tick()`——这是刻意的：引擎不知道宿主的时钟，也不该自己起 interval。

### 10.3 生命周期

```
createChat()  → 建目录、读 pinned/pending、整理旧 said 文件
   │
   ├─ say() / tick() / forceSpeak() 反复调用
   │
   └─ close() → 把 pending 里的对话整理掉（进程退出前调；不调也不会丢，
                下次启动会从 .pending.json 补）
```

进程被强杀也不丢对话：`record()` 是同步写 `raw/` 和 `.pending.json` 的。

## 11. 接到别的宿主

### 11.1 图形界面

```js
const chat = createChat({ apiKey, dataDir, isHere, idleSec, onSpeak });
const r = await chat.say(input);
for (const seg of r.segments) await showBubble(seg);   // 一条一条显示
setInterval(() => chat.tick(), 30000);                  // 30~60 秒
```

`onSpeak` 收到的是单条文本，直接显示即可。

### 11.2 IM（QQ / Telegram / Discord）

要点只有三个：

1. **一个用户一个实例、一个 `dataDir`** —— 记忆没有 user id 维度
2. **`isHere` 用"最近说过话"代替"鼠标动过"** —— 否则 `tick()` 永远认为人在
3. **`onSpeak` 要绑定目标会话** —— 框架只给文本，不记"该发给谁"

```js
const bots = new Map();
const getBot = (uid) => {
  if (!bots.has(uid)) {
    bots.set(uid, createChat({
      apiKey: process.env.DEEPSEEK_API_KEY,
      dataDir: `./data/${uid}`,
      isHere: () => Date.now() - (lastSeen.get(uid) || 0) < 30 * 60000,
      onSpeak: (text) => send(uid, text),
    }));
  }
  return bots.get(uid);
};
```

群聊额外注意：`segments` 是 1~3 条，群里建议拼成一条；主动开口在群里很容易变成刷屏，建议关掉或大幅降频。

### 11.3 只要记忆、不要对话

```js
const { modules } = require('bigfish-chat');
const mem = modules.memory.createMemory({ dir: './memory', complete: myLlmCall });
mem.init();
mem.record('用户说了什么', '它回了什么');
await mem.flush('手动');
console.log(mem.context('当前这句话'));
```

## 12. 成本结构

### 12.1 单次请求到底有多大（实测）

用 `createChat` + 假接口把请求体抓下来量的，中文按官方 **1 字 ≈ 0.6 token** 折算。构造的是"满记忆"：pinned 撑满 220 字、今天 8 条、昨天 5 条、前天 4 条、周摘要 26 份、月摘要 12 份。

| 场景 | system 字数 | 其中记忆块 | 命中 token | 未命中 token | 合计 |
|---|---|---|---|---|---|
| 空记忆（刚装上、还没聊过） | 2354 | 0 | 1376 | 39 | 1415 |
| 满配 / 默认 `memoryMaxChars=1400` | 3750 | 1269 | 1376 | 877 | 2253 |
| 满配 / `memoryMaxChars=1800` | 3750 | 1269 | 1376 | 877 | 2253 |

命中那 1376 token 是 `persona.js` 的固定前缀（实测 2294 字），每轮都一样，走缓存命中价。未命中就是记忆块 + 这句用户输入。

**两个反直觉的地方：**

1. **`memoryMaxChars` 从 1400 调到 1800，一个字都不多。** 卡住注入量的是条数上限（今天 8 条 / 昨天 5 条 / 前天 4 条 / 周摘要 220 字 / 月摘要 200 字），不是字数上限 —— 1269 字时名额已经满了，再多给预算也塞不进新东西。反过来说，**调小到 1000 才会真的变短**（实测注入 1014 字、未命中约 650 token）。
2. **注入量几乎与"每天聊多少轮"无关**。一天 10 轮和一天 100 轮，注入的都是那几条摘要，不会随对话量膨胀。这也是它敢跑步数年的原因。

### 12.2 每次调用多少钱

DeepSeek V4.1 Flash 官方价（2026-10，美元/百万 token）：输入未命中 0.15、命中 0.003、输出 0.6（off-peak）；高峰时段全部翻倍。按 7.1 汇率折算：未命中 1.065 元/百万、命中 0.0213 元/百万、输出 4.26 元/百万。

| 调用 | 单次成本（off-peak） |
|---|---|
| 对话 · 空记忆 | 0.00033 元 |
| 对话 · 满配（默认 `memoryMaxChars=1400`） | 0.0012 元 |
| 对话 · 满配 `memoryMaxChars=1800` | 0.0012 元（同上，条数先封顶，加字不涨） |
| 整理（一批 3800 字符） | 约 0.0025 元 |
| 复核（一天日记） | 约 0.001 元 |
| 周摘要 / 月摘要（一批重点行） | 各约 0.0019 元 |
| 主动开口 | 约 0.00008 元 |
| 二次展开 | 约 0.0001 元 |
| 预热 | 约 0.001 元，换来之后全部走命中价 |

**用真实账号校准过**：空记忆按上表算 20 轮是 0.0066 元，实测 **0.01 元**，是表算的约 1.5 倍（实际输出比预算的 60 token 长，另有一部分落在高峰时段）。按这个偏差折算，**满配默认约 0.0018 元/轮**。

### 12.3 跑一年要多少钱

按每天 50 / 100 轮、默认 `memoryMaxChars=1400`、`memoryIdleMinutes=10`、满配 0.0018 元/轮估：

| 项目 | 100 轮/天 | 50 轮/天 |
|---|---|---|
| 对话 | 66 元 | 33 元 |
| 整理（约 10 次/天） | 3.3 元 | 1.7 元 |
| 复核（每天 1 天） | 0.4 元 | 0.4 元 |
| 周摘要 + 月摘要 | 0.2 元 | 0.2 元 |
| 主动开口（≤6 次/天） | 0.2 元 | 0.2 元 |
| 二次展开 | 0.1 元 | 0.1 元 |
| **合计（全在错峰时段）** | **约 70 元** | **约 36 元** |

工作日 9–12、14–18 是高峰（单价翻倍）。按 3~4 成调用落在高峰估：**100 轮/天 90~98 元/年，50 轮/天 46~50 元/年**。

### 12.4 想省钱先动哪里

**日成本的大头是对话本身，不是整理**，但这三件事值得知道：

1. **`memoryIdleMinutes` 别往小调**。整理成本由"整理次数"决定，不由"聊了多少"决定 —— 每次都要重发一份约 2000 字的分类提示词。从 10 分钟降到 3 分钟，整理次数翻三倍，一年多花 4~5 元，换来的只是"日记更贴细节"。
2. **精简人设省不了钱**。2294 字的 persona 全部走命中价，每轮只花 0.00003 元。砍掉一半人设，一年省不到 1 块钱。
3. **真能省的是未命中那部分**：`memoryMaxChars` 从 1400 降到 1000（实测注入 1269 → 1014 字，未命中 token 约省 26%）、`historyTurns` 从 2 降到 1。代价都是记忆质量。

### 12.5 账本

所有调用（对话 / 整理 / 复核 / 主动 / 预热）都从 `llm.js` 这一个出口走，按类型分记、一天一个文件，只记接口真的返回了的数字，不猜不估。以前只在控制台打一行推理 token，账面看不见"今天到底花了多少"，反推又总会漏掉整理、复核、预热这些隐形调用。

## 13. 设计取舍

1. **真实感优先于召回率**：日记 2~6 条、每条 30 字，零命中就沉默。编造是真实感最大的破坏者。
2. **不做向量检索**：一查就准的东西不叫记忆，叫数据库。
3. **不追未说完的话题**：主动追问"上次那个故事"是助理行为，不是人。
4. **记忆只调重要性、不删除**：降级是"这条没那么重要"，不是"这条不存在"。
5. **情绪方向交给模型**：只给事实，不写"该生气还是该难过"。
6. **零依赖**：想读的人打开就能读，想跑的人不用先装几百个包。

## 14. 已知限制

| 限制 | 说明 |
|---|---|
| 非流式 | 一次返回完整回复再拆条；做流式要改 `llm.js` 与分段 |
| 中文优先 | 分词按字符滑窗、提示词中文；换语言要改 `grams()` 和提示词 |
| 单用户 | 记忆没有 user id 维度，多用户必须多实例 |
| raw 按自然日切 | 跨 00:00 的对话落两个文件；日记层有就近归日容错，raw 层没有 |
| `say()` 无队列 | 并发调用可能让历史顺序错乱，宿主需串行 |
| 无重试 | API 网络失败不自动重试（只有 `thinking` 字段不兼容会重发一次） |
| 成本随定价 | 单轮 0.0003~0.0018 元取决于记忆满不满，一年账单见 §12；换模型或调价就重新算 |
| 情绪是整段的 | 一次堵气两小时，不会自己淡出得越来越自然 |
| pinned 满了挤老条目 | 220 字满额后，最早钉住的约定先从注入里退出（文件里还在） |
| 日记不淘汰 | `diary/` 一天一个文件永久保留，只有检索范围可配（默认 365 天） |
| 多实例不设锁 | 两个进程指向同一个 `dataDir` 会抢写同一批文件，一个宿主只开一个实例 |
